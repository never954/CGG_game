# Assignment 6: building the game in Godot (study guide)

> For the deep dive on every system (how sprites are drawn, combat, AI, camera maths…) see
> **[HOW_IT_WORKS.md](HOW_IT_WORKS.md)**.

This guide walks through how this game is made in the **Godot engine**, step by step, in the order
the assignment asks. Each section says **where to click in the editor**, **which file does it**, and
**what to say if the teacher asks**.

---

## 0. Opening the project (do this first)

1. Double-click **`Open in Godot.command`** in the `game_play` folder.
   (Or open Godot → *Import* → choose `game_play/project.godot` → *Import & Edit*.)
2. Press **F5** (or ▶ at the top right) to run from the title screen.
   **F6** runs only the scene you have open. **F8** stops.
3. If Play ever freezes: that is the Metal driver on macOS. The project already uses Vulkan
   (*Project → Project Settings → Rendering → Rendering Device → Driver (macOS)*).

## 1. Game engine setup

- Engine: **Godot 4.7** (free, open source), installed with `brew install --cask godot`.
- Renderer: **Forward+** (the full 3D renderer, needed for volumetric fog, SSR and SSAO).
- Language: **GDScript** (Python-like, built into Godot).
- A Godot project is a folder with a `project.godot` file. `res://` means "the project folder";
  `user://` means "the per-user data folder" (where the save file goes).

**Viva**: *Why Godot?* Free, lightweight, a scene/node system that maps cleanly onto game objects,
a built-in scripting language, and one-click export to Mac/Windows/Linux/Web.

## 2. The editor interface

| Panel | Where | What it is for in this game |
|---|---|---|
| **Scene tree** (Scene dock) | top left | the nodes of the open scene, e.g. `Player → Shape, Sprite, Hitbox` |
| **FileSystem** | bottom left | `res://`: `assets/`, `scenes/`, `scripts/` |
| **Inspector** | right | properties of the selected node; the `@export` variables in scripts appear here |
| **Viewport** | centre | 2D / 3D / Script tabs; the 3D view shows levels because the builder is `@tool` |
| **Output / Debugger** | bottom | `print()` output, errors, the profiler and the FPS monitor |

Try: open `scenes/world/level_preview.tscn`, click **Level**, change **Level Index** in the Inspector,
and the level rebuilds in the 3D view.

**Key idea: nodes and scenes.** Everything is a *node* (a camera, a light, a sprite, a collision shape).
A *scene* is a saved tree of nodes (`.tscn`). Scenes can be *instanced* inside other scenes: every
frog is an instance of `scenes/actors/hopper.tscn`.

## 3. Input mapping

- File: `scripts/autoload/controls.gd` (an **autoload**: *Project Settings → Globals → Autoload*).
- It registers **actions** (`move_left`, `jump`, `attack`, `heavy`, `block`, `dodge`, `interact`, `pause`)
  and binds keyboard keys and gamepad buttons/sticks to them.
- Gameplay code never asks "is the J key down?". It asks `Input.is_action_just_pressed("attack")`,
  so rebinding keys or adding a gamepad needs no gameplay changes.
- `Input.get_axis("move_left", "move_right")` gives −1…1 for keys and the analog stick alike.

**Viva**: *What is an action?* A named input event that many keys/buttons can trigger
(*Project Settings → Input Map* shows them while the game runs).

## 4. Sprites, characters and animation

- Art is generated by **our own C++ rasterizer** (`tools/assetgen.cpp`), using the course algorithms:
  scan-line polygon fill, 2D transformation matrices (rotation/scale/translation for each body part),
  outlines. It writes PNG sprite sheets plus a JSON file describing the animations.
- `scripts/actors/sheet_sprite.gd` (an `AnimatedSprite3D`) reads the JSON and builds a
  **SpriteFrames** resource: one animation per row (`idle`, `run`, `jump`, `attack1`, `heavy`, …),
  each with its own frame rate and looping flag.
- The player script switches animations by state (`sprite.play("run")`) and checks
  `sprite.frame` so damage happens only on the **active frames** of an attack.
- Facing left = `flip_h`. The sheets keep the feet centred so flipping never shifts the character.

## 5. Level / tile design

- Levels are text tile maps (`assets/levels/level_N.txt`, see `docs/LEVELS.md`).
- `scripts/world/level_builder.gd` turns each map into:
  - **terrain meshes** built with `SurfaceTool` (textured tops, cliff faces, depth shading in vertex colours),
  - **collision**: solid tiles merged into as few `BoxShape3D`s as possible (greedy merge),
  - one-way **platforms**, **water** with a drowning `Area3D`, and every **object** from its letter,
  - the **diorama**: river bank, trees, reeds, lanterns with lights, lakes, hills and mountains.
- Five levels, Swordigo style: islands over water, a crate puzzle, wall-jump shafts, keys & gates,
  thorn pits, a brute arena, and the boss throne.

**Viva**: *Why not draw each level by hand in the editor?* The text format is quick to edit and
version-control, and it guarantees that collision always matches the visuals. It is still visible in the
editor through the `@tool` preview scene.

## 6. Collisions and physics

| Body type | Used for | Why |
|---|---|---|
| `CharacterBody3D` | hunter, enemies | movement under full script control via `move_and_slide()` |
| `StaticBody3D` | terrain, platforms, gates | things that never move |
| `RigidBody3D` | crates | real physics: pushed, knocked, stacked, falls |
| `Area3D` | pickups, shrines, exit, water, thorns, attack hitbox | detects overlap without blocking |

- **Collision layers/masks** (*Project Settings → Layer Names → 3D Physics*): what a body *is* (layer)
  and what it *collides with* (mask). See the table in `DESIGN.md`.
- **One-way platforms**: the player turns platform layer 3 in its mask *on* only while falling.
- **Gravity**: custom (30 m/s², ×1.5 when falling) for a crisp platformer arc.
- **Attacks**: an `Area3D` hitbox in front of the hunter. `get_overlapping_bodies()` on the active frames
  finds what was hit, and each body is hit once per swing.

## 7. Gameplay systems

- **Player** (`player.gd`): state machine (NORMAL, ATTACK, HEAVY, LAUNCH, AIR_ATTACK, DIVE, AIR_DASH, DODGE,
  BLOCK, HURT, DEAD, TALK, SPECIAL), coyote time, jump buffer, wall jump, stamina, spirit meter,
  launcher/juggle/dive, parry, perfect dodge, Moon Breaker, powers unlocked by memories.
- **Enemies** (`enemy.gd` base class + `hopper.gd`, `brute.gd`, `cultist.gd`, `toad_king.gd`):
  inheritance; each subclass only writes its `think()` behaviour. Randomised telegraphed attacks, feints,
  evasion, combos, ranged daggers, attack slots, boss phase 2.
- **Collectibles**: orbs, peaches, keys, memory eyes (`pickup.gd`). **Doors**: `gate.gd` uses a key.
- **Checkpoints**: `shrine.gd` → `GameState.reach_checkpoint()` → saves to `user://save.cfg`.
- **Story NPC**: `npc.gd` (Old Koax), with conversations in `assets/dialogue/story.json`.
- **UI**: title screen, HUD (hearts, stamina, orbs, keys, memories, boss bar), dialogue, pause, game over,
  level complete, ending.

## 8. Audio

- 27 sound effects + 4 music loops in `assets/audio/`, **synthesised** by `tools/audiogen.py`
  (plucked strings, frog croaks, bells, filtered noise).
- `scripts/autoload/audio.gd`: a pool of `AudioStreamPlayer`s, so many sounds can overlap, with random
  pitch so repeated sounds don't feel robotic. Music cross-fades with a **Tween** and loops.
- Used everywhere as `Audio.sfx("hit")` / `Audio.music("music_marsh")`.

---

## 9. Camera and rendering

- `scripts/camera/camera_rig.gd`: delayed spring follow, look-ahead, combat zoom and swing, air tilt,
  FOV punch, screen shake, depth of field. See `DESIGN.md` for the maths.
- `WorldEnvironment` (built per level): procedural sky, fog + volumetric fog, SSAO, SSR (water
  reflections), glow, filmic tonemapping. `DirectionalLight3D` sun with shadows; `OmniLight3D` lanterns.
- Water: a custom **shader** (`water.gdshader`) with animated ripples and a Fresnel colour mix.

---

## 10. Testing and debugging

- **Debugger → Monitors**: FPS, draw calls, physics objects. The game runs at ~60 FPS on the M2.
- **Remote scene tree** (Scene dock → *Remote* while running): inspect live nodes and positions.
- **Visible collision shapes**: *Debug → Visible Collision Shapes*, then run.
- Automated bot: `tools/autotest.tscn` loads a level, simulates input and takes screenshots. It checked
  that the wall-jump shafts can be climbed, crates can be pushed onto ledges, platforms can be jumped
  through and dropped through, and every key/eye/exit is reachable.
  ```bash
  godot --path . res://tools/autotest.tscn -- --level=1 --climb=106.5
  ```

## 11. Exporting a build

1. *Editor → Manage Export Templates → Download and Install* (one-time, ~1 GB).
2. *Project → Export… → Add… → macOS* (or Windows Desktop).
3. Set the export path to `export/Brekekekex.app` (or `.zip`) and click **Export Project**.
4. The result runs without Godot installed.

## Quick viva answers

- **Scene vs node?** A node is one building block; a scene is a reusable saved tree of nodes.
- **What is an autoload?** A script Godot loads once at startup that stays alive across scene changes
  (GameState, Audio, Controls). It works like a global singleton.
- **_process vs _physics_process?** `_process` runs every rendered frame; `_physics_process` runs at a
  fixed 60 Hz and is used for movement and collisions so they are stable.
- **What is `delta`?** Seconds since the last frame; multiplying by it makes motion frame-rate independent.
- **Signals?** Godot's observer pattern: `player.died.connect(_on_player_died)`.
- **Groups?** Tags on nodes (`"enemy"`, `"camera"`), so code can find or call them without hard links.
- **How is the game saved?** `ConfigFile` written to `user://save.cfg` when a shrine is lit.
- **How does the camera follow "with delay"?** A damped spring: acceleration toward the target minus
  velocity damping, integrated every frame.
- **What is hit-stop?** Briefly slowing `Engine.time_scale` (to 5%) on impact, so hits feel heavy.
- **Why sprites in 3D?** HD-2D: pixel-art characters get real lighting, shadows, fog and reflections.
